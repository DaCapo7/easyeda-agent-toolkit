# 料号核验清单（模板）

用法：选型调研给出候选之后、把料号写进 BOM 之前，逐条走完这份清单。
本模板不依赖任何特定 AI 产品。执行者可以是人，也可以是 AI。

---

## 为什么必须核验

后续的网表导入按 `Supplier Part`（立创 C 编号）查库放器件。这个字段有三个特性：

1. **只有它参与匹配。** 厂商型号和封装名都不参与，编号错了就是放上一个错器件。
2. **事后无法修正。** `modify` 改不了器件的库关联，唯一的解法是改网表 JSON 重新导入。
   界面上的「器件标准化」也救不了 —— 它只会标准化成那个错编号指向的器件。
3. **编号会下架。** 曾经有效的编号，过一段时间可能在库里查不到了。

所以这一关只能在写进 BOM 之前做对，后面没有补救窗口。

---

## 强制纪律

> **任何 C 编号，必须在器件库中实际检索命中之后才算数。**
>
> 命中的含义是三条同时成立：
> **(1) 检索确实返回了这个编号对应的器件；(2) 库存 > 0；(3) 封装与关键参数逐项对得上规格。**
>
> **严禁凭记忆、印象或"看起来像"给出编号。** 语言模型对元器件编号的记忆极不可靠：
> 编号格式规整、长度固定，很容易生成出一个格式完全正确但根本不存在、
> 或者存在但对应完全不同器件的编号。这类错误在导入之前没有任何症状。
>
> 没有实际检索过的编号，一律标记为「未核验」，不得写进 BOM。

---

## 核验通道

两条通道，任选其一即可，两条都走更稳。

### 通道 A：网页库检索

在立创商城 / 嘉立创元件库的网页检索界面，按编号或厂商型号查询。

记录：编号、厂商型号、封装、关键参数、库存、价格、库别（基础库 / 扩展库）、读取时间。

这条通道任何人都能用，不需要装任何东西。

### 通道 B：经桥在 EDA 客户端内查库

如果已经按仓库 README 装好了官方 easyeda-api-skill 的桥和 run-api-gateway 扩展，
可以直接查 EDA 客户端连着的器件库。这条通道的好处是：**查到的就是导入时会用的那个库**，
不存在"网页上有、客户端库里没有"的偏差。

仓库里的 `examples/30_library_search.js` 就是干这个的：

```bash
# 改脚本里的 KEY(关键词) 或 LCSC_IDS(要核验的 C 编号), 然后
python tools/eda_bridge.py run examples/30_library_search.js
```

它封装了两个 API（签名取自官方 easyeda-api-skill 的 `LIB_Device` 参考）：

```js
// 关键词检索, 返回候选列表
eda.lib_Device.search(key, libraryUuid?, classification?, symbolType?, itemsOfPage?, page?)

// 按 C 编号精确取器件; 返回空 = 这个编号在库里不存在
eda.lib_Device.getByLcscIds(lcscIds, libraryUuid?, allowMultiMatch?)
```

检索结果里可以拿到厂商、厂商型号、供应商编号、封装、库存、价格，以及库别
（`"standard"` = 基础库，`"extend"` = 扩展库）。

> **字段位置的注意事项。** 官方参考里，商业类字段（库存、价格、库别、供应商编号、厂商）
> 在顶层已标记为 obsolete，说明改到 `otherProperty` 里。顶层字段可能仍然存在，也可能为空。
> 所以 `30_library_search.js` 会同时打印 `otherProperty` 的**原始键名**和归一化后的结果 ——
> 先看一眼你这个版本实际给了什么，再决定怎么解析，不要照抄别处的字段名。

## 逐条清单

对每一个准备写进 BOM 的编号，逐项打勾。任何一项不通过，这个编号就不能用。

### 1. 存在性

- [ ] 编号在库里**实际检索命中**（不是凭印象，不是从别处抄来的）
- [ ] 检索返回的器件名称 / 描述，与预期的器件类别一致（别把电阻查成了电容）
- [ ] 记录了检索时间与所用通道

### 2. 库存

- [ ] 库存 > 0
- [ ] 库存量 ≥ 需求量，且留有余量（备料损耗、返工、第二批）
- [ ] 记录了库存数值与读取时间（库存随时会变，没有时间戳的数字没有意义）

### 3. 封装

- [ ] 库里的封装名，与 BOM / 网表里写的封装名一致
- [ ] 封装的物理尺寸符合板上的布局预留
- [ ] 引脚数与引脚间距对得上原理图符号
- [ ] 确认过是贴片件还是插件件 —— 插件件在纯 SMT 产线上需要单独手焊，必须提前告知

### 4. 参数

逐项对照选型规格，不是只看一眼总体印象：

- [ ] 关键参数 1：〈规格要求〉 vs 〈实际值〉
- [ ] 关键参数 2：〈规格要求〉 vs 〈实际值〉
- [ ] 关键参数 3：〈规格要求〉 vs 〈实际值〉
- [ ] 工作温度范围覆盖使用条件
- [ ] 精度 / 容差满足要求
- [ ] 参数来源是厂商数据手册，且记录了手册版本或日期

### 5. 商务与工艺

- [ ] 库别已确认（基础库 / 扩展库），扩展库的上料费影响已评估
- [ ] 单价在预算内，且注明了对应批量
- [ ] 生命周期状态正常（非 NRND / EOL）
- [ ] 厂商型号（MPN）已记录 —— 编号下架时靠它找现行替代

### 6. 一致性

- [ ] BOM 里的 `Supplier Part` 与本次核验的编号**逐字符一致**
- [ ] BOM 里的 `Manufacturer Part` 与库里的厂商型号一致
- [ ] BOM 里的 `Footprint` 与库里的封装一致
- [ ] 同一个器件在不同板 / 不同 BOM 行里用的是同一个编号

## 输出格式

```
核验时间：〈YYYY-MM-DD HH:MM〉
核验通道：〈网页库检索 / 经桥查库 / 两者〉

| 位号 | 供应商编号 | 厂商型号 | 封装 | 库存 | 库别 | 参数逐项 | 结论 |
|---|---|---|---|---|---|---|---|
| 〈R1〉 | 〈示例：0402 10kΩ 这类通用件按实际检索结果填写〉 | | | | | 全部对上 | 通过 |

未通过项：
- 〈编号〉：〈哪一项不通过，差多少，怎么处理〉

未核验项：
- 〈编号〉：〈为什么没核验，缺什么条件〉
```

「未核验项」这一节可以为空，但不能省略 —— 它是这份清单的诚实性检查点。

## 导入之后的复核

编号写进 BOM、网表导入完成之后，还有两道自动化复核，都在本仓库里：

1. **`tools/fix_supplier_ids.py`** —— 网表重建导入之后，器件的 SupplierId 常被设成厂商型号
   而不是 C 编号，会触发 DRC 的「供应商不符」。这个脚本按位号把编号批量刷回去。
   它读的是你的网表 JSON，所以**网表里的编号错了，它只会把错的刷得更整齐** ——
   这就是为什么核验必须在写进 BOM 时完成，而不是指望这一步兜底。

2. **`tools/compare_netlist.py`** —— 源网表与导出结果逐脚比对，确认导入没走样。

两者都不检查「这个编号对不对」，只检查「编号有没有被正确传递下去」。
编号本身的正确性，只有这份清单能保证。
